# QA-1041-UNREAD correction

The React navigation read-state view now retains an authorized HTTP detail refresh while mounted. Previously, selecting another conversation released the DM stream, leaving its unread and mention counts stale until a reconnect or reload. `useReadState` shares the existing client unread-mention reconciler rather than opening additional message streams.

The reconciler requests a snapshot when the first view mounts and then every five seconds. There is one timer per client, one queued request per conversation and at most four concurrent requests. Duplicate views share ownership; the last release aborts its pending read. Slow requests do not accumulate polling work. Navigation virtualization bounds the mounted rows. Browser timer throttling, network latency and the queue can extend the refresh interval; this is eventual HTTP freshness, not a push-delivery guarantee.

Each tab reads through its own authenticated HTTP boundary, so a follower does not rely on its socket-owning sibling having the same mounted conversations. No new WebSocket subscription, server event, message payload broadcast, database migration or protocol version is required. Counts remain server-authoritative. Mute and explicit thread unfollow retain their existing semantics. A manual unread marker received from another client also pauses the visible timeline's automatic read observer, using the same pause as the local Mark unread action. A new intentional reading gesture resumes automatic reads; incidental layout changes do not clear the marker.

Reconnect keeps the existing authoritative snapshot reconciliation. Identity changes and close invalidate queued/in-flight reads and clear ownership. Snapshot guards prevent a late read from replacing newer cursor or membership state. Explicit stream revocation, an observed private membership removal, or an authenticated detail response of 403/404 discards the cached conversation, its unread state and inherited thread content. Those rows stop polling; rediscovery requires fresh authorized data. Transient transport failures retain the last state and retry on the bounded interval.

The optional `ChatClient.retainReadState` method allows an existing custom client implementation to remain structurally compatible. SDK-created clients provide it. `useReadState` owns the lifecycle, including client/session changes and unmounting; callers should not manually retain each navigation row.

Durable regression: `examples/drop-in-react/e2e/chat-lab.background-unread.spec.mjs`. It asserts both same-origin Grace tabs show one unread message and one mention before any reconnect/reload; exercises duplicate cursor commands, advancement, manual unread, recovery and clear; and checks private access removal without continued polling or message leakage. The test attaches bounded UI captures and runtime/source identities. Run with the existing canonical PostgreSQL Chat Lab fixture, one Playwright worker and zero retries.

Focused runtime and React hook tests cover timer ownership, four-request concurrency, cancellation, cursor/manual unread, muted/unfollowed state, denial, session/tenant boundaries and late replies. Existing cross-tab bootstrap and thread tests remain part of the correction checks. The producing work request's deliverable manifest retains exact patch/source hashes, independent baseline/corrected results, commands, failures, screenshots and cleanup receipts.

This is a scoped unread correction. Full SDK readiness, huddle/native/device coverage, external provider delivery, a reviewed installable release and owner approval before Hitcents ERP adoption remain separate gates. Flutter and preview revisions, effective authentication rate limiting (10 requests/60 seconds), and all release/deployment permissions remain unchanged. The worker leaves source uncommitted and does not bump package versions.
