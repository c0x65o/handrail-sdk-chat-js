# QA-1041-UNREAD correction

The React navigation read-state view retains an authorized HTTP refresh while mounted. Previously, selecting another conversation released the DM stream, leaving its unread and mention counts stale until a reconnect or reload. `useReadState` shares the existing client unread-mention reconciler rather than opening additional message streams.

The reconciler uses the authoritative conversation-list projection for mounted top-level read-state observers. One page (up to 100 rows) starts at most every five seconds per client. It walks opaque continuation cursors until it has covered the retained rows or exhausted the list. Refresh hydration preserves the consumer's discovery pages, pagination, and selection; it applies only guarded projections for still-retained, accessible conversations. Initial discovery already supplies read state, unread/mention counts, membership, preferences, and latest sequence.

Threads, event-triggered reconciliation, and list-absent rows use a separate detail queue, with at most one detail start every five seconds. List absence is not treated as permission denial: a detail 403/404 confirms revocation. Duplicate views share ownership; release/close aborts owned work. A slow request does not accumulate timer work. Dirty detail requests move to the back of the queue for fairness. Together the two lanes permit at most two concurrent reads and 24 scheduled starts per half-open minute, independent of mounted row count. Authentication retries retain the existing snapshot-reader behavior.

This bound also applies to hidden retained workspaces; no host visibility/remount integration is required. Freshness is eventual: large lists require multiple page intervals, direct observers share the detail cadence, and browser throttling or slow transport can extend convergence. No message stream or unread feature is disabled.

HTTP 429 pauses both lanes through the latest outstanding Retry-After deadline. Delta seconds and HTTP dates are supported; absent/invalid/past headers use a conservative 60-second fallback. Deadlines survive release, close, and reopen so remounting cannot hammer the server. Overlapping failures cannot shorten the cooldown. Custom fetch adapters should preserve the optional response `headers.get` interface to honor server deadlines longer than the fallback. This is a bound on unread reconciliation, not a replacement for the consumer's shared API limiter or a guarantee for arbitrary additional host traffic.

Each tab reads through its own authenticated HTTP boundary, so a follower does not rely on its socket-owning sibling having the same mounted conversations. No new WebSocket subscription, server event, message payload broadcast, database migration or protocol version is required. Counts remain server-authoritative. Mute and explicit thread unfollow retain their existing semantics. A manual unread marker received from another client also pauses the visible timeline's automatic read observer, using the same pause as the local Mark unread action. A new intentional reading gesture resumes automatic reads; incidental layout changes do not clear the marker.

Reconnect keeps the existing authoritative snapshot reconciliation. Identity changes and close invalidate queued/in-flight reads and clear ownership. Snapshot guards prevent a late read from replacing newer cursor or membership state. Explicit stream revocation, an observed private membership removal, or an authenticated detail response of 403/404 discards the cached conversation, its unread state and inherited thread content. Those rows stop polling; rediscovery requires fresh authorized data. Transient transport failures retain the last state and retry on the bounded interval.

The optional `ChatClient.retainReadState` method allows an existing custom client implementation to remain structurally compatible. SDK-created clients provide it. `useReadState` owns the lifecycle, including client/session changes and unmounting; callers should not manually retain each navigation row.

Durable regressions: `examples/drop-in-react/e2e/chat-lab.background-unread.spec.mjs` and `examples/drop-in-react/e2e/chat-lab.read-state-polling.spec.mjs`. The latter creates 24 authorized private channels, runs two independent consumers with realtime disabled, bounds foreground/hidden requests, and checks selection and an unsent draft after returning. It asserts both same-origin Grace tabs show one unread message and one mention before any reconnect/reload; exercises duplicate cursor commands, advancement, manual unread, recovery and clear; and checks private access removal without continued polling or message leakage. The test attaches bounded UI captures and runtime/source identities. Run with the existing canonical PostgreSQL Chat Lab fixture, one Playwright worker and zero retries.

Focused runtime and React hook tests cover row-independent volume, paced pagination and direct-observer fairness, timer ownership, cancellation, cooldown and overlapping 429s, cursor/manual unread, muted/unfollowed state, denial, session/tenant boundaries and late replies. Existing cross-tab bootstrap and thread tests remain part of the correction checks. The [bounded-polling qualification record](read-state-polling-20261006/qualification.json) retains source identities, checks, limitations, and links to compressed endpoint/conversation/client/visibility traces and cleanup receipts. The baseline recorded 854 request attempts versus 51 after the correction over the same 75-second workload; the maximum rolling 60-second GET count fell from 679 to 38. Both runs had zero HTTP429 and zero 5xx. This reproduces request growth, not exact attribution of the earlier Preview staging 429s. Actual Preview database-window counts and paired Flutter/background host traffic remain unverified.

Flutter and Preview revisions remain unchanged. The consumer ordinary API budget remains 120 requests per verified user per 60-second database window across devices/SDKs; authentication/session and cancellation retain their separate budgets. No limiter or release/deployment setting changed. The worker leaves source uncommitted and does not bump package versions.
