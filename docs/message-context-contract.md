# Bounded message source context

`contracts/http/message-context.json` defines `GET /conversations/:conversationId/messages/:messageId/context`. The path parameters form `MessageContextRequest`; there is no query, request body, page scan, or cross-conversation fallback. Both IDs use canonical identifier types and must be nonempty, unpadded, control-free strings of at most 255 UTF-8 bytes. The generated parsers reject additional request fields, including caller-supplied actor, tenant, and permission data.

A successful HTTP 200 read returns exactly one of these bodies:

| status | fields beyond status and the two requested IDs |
| --- | --- |
| `available` | `sequence`, `message`: the active canonical `Message` |
| `deleted` | `sequence`, `message`: the canonical deletion shell, with `content: null` and both deletion metadata fields |
| `unavailable` | none |

All results echo the requested IDs. An available/deleted message must have the same conversation and message IDs, and its sequence must equal the result sequence. Sequences are positive safe integers (1 through 9007199254740991), matching the canonical message validator. Zero remains an allowed timeline cursor, not an allocated source message position. Canonical `replyTo` and thread metadata remain canonical metadata; this read does not manufacture a forward snapshot or persist source content.

The result sequence can be used with the existing timeline contract's exclusive backward/before and forward/after cursors. The target arrives separately because both adjacent pages exclude it. Existing timeline routes, pagination, and replay semantics remain unchanged. This endpoint returns at most one message, not surrounding pages or an unbounded search. Clients must still reconcile subsequent deletion/access changes; this response is not a permission grant or a durable content cache.

Authorization belongs to the server's trusted tenant and actor context and current conversation/message access checks, including inherited parent access for threads. Identifiers and client preferences do not prove permission. An inaccessible target (including a deleted target without access), an absent target, and a target outside the requested conversation all produce the same `unavailable` body for the same request. It contains only the requested identifiers and status, never content, sequence, reason, existence flags, or source metadata. The server must also avoid distinguishing these cases through target-specific HTTP status or diagnostic details.

Transport errors are outside `MessageContextResult`: timeouts, connection failures, rate limiting and transient server errors remain failures that a later transport/controller can retry. Authentication/session and other non-success HTTP responses also remain transport errors. Do not translate a rejected request, non-success HTTP response, or parse exception into `unavailable`. Only a successfully parsed HTTP 200 result can establish unavailable. The parser requires the expected request and throws on malformed or incoherent responses. This change implements no HTTP execution, retry policy, server query/route, controller, UI, or persistence.

Generation: `npm run generate:message-context`; drift check: `npm run check:message-context`. TypeScript reuses the exported canonical validator generated by `generate-send-message.mjs`; Dart reuses `Message.fromJson` and canonical identifier parsers. Templates add the endpoint's stricter identity, sequence, status, and deletion-redaction constraints.
